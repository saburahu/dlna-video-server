# v0.4.5 起動・キャッシュ照会の改善（開発候補）

## 変更の範囲

- メタデータ照会を最大8件に制限して並列実行する。全照会の完了を待ってから起動時のHTTP待受へ進む。配列順序、後から公開された新しいメタデータを上書きしない条件、UpdateIDの更新単位を維持する。
- 同一照会内で取得済みの物理ファイルIDとキャッシュstatを再利用する。JSON読込み後にも物理IDを照合し、同じsize/mtimeの別ファイルへの置換を拒否する。ソースの最終size/mtime、JSONサイズ上限、schema、内容検証、SHA-256、旧形式へのフォールバック、保存先分離検査は維持する。照会結果の永続化や長寿命のメモリキャッシュは追加しない。
- PCRキャッシュのディレクトリを完全に検査した後、既存SQLite管理表の更新を1トランザクションへまとめる。ファイルシステムの待機中にDBロックを保持しない。列挙失敗時は既存表を保持する。停止時は列挙を中断し、起動中処理を回収してからDBを閉じる。DB schema、PCR索引、キャッシュの形式は変更しない。
- v0.4.4では番組時間軸の公開側が既定ONである一方、解析証拠の保存・旧キャッシュ補完は環境変数が明示的に1の場合に限られていた。解析側も既定ON／明示0でOFFへ揃える。証拠不足の録画を受理する変更ではなく、既存の低優先度解析で必要な証拠を取得する。起動時間短縮とは別の互換性修正である。

再生、PCR/PTS、TimeSeek、色変換、音声、JITの実装は変更しない。旧ObjectID・URL、仮想フォルダー、1録画1項目、番組適格性の条件も維持する。旧版への復旧時にキャッシュの再変換は不要。

## 測定方法と限界

Windows／Node.js 24.22の同一環境で、5000本の独立した合成TSを使用する。元録画は使用・変更しない。待受はloopbackの自動割当ポートのみ、SSDP広告は無効。OSキャッシュの強制消去やセキュリティ設定の変更は行わない。

起動からHTTP待受、管理API、最初の正しいBrowse、全件探索完了を分けて計測する。カタログなしの初回起動で空の一覧を返す時刻を完成とは数えない。JSON処理、非同期ファイル操作、同期パス分離検査、CPU時間、RSSを軽量な外部observerで採取する。通常起動ではobserverを読み込まず、計測ログも追加しない。

メタデータあり・なし・10%欠落・10%破損・カタログなしを各3回測定する。保存済みPCRについては5000件の小さな合成索引を使用し、背景生成を停止した独立測定で、同じキャッシュを再起動して照会する。通常の背景解析を使うシナリオとは区別する。

合成TSにはEIT番組がなく、5000本全部の番組時間軸が即時に利用可能になる証拠ではない。実録画のメタデータ・番組再生は別のPC HTTP検証で確認する。初めての全編SI解析、大きな実PCR索引の読込み、実機の互換性向上を速度結果から推定しない。

## 基準値

安全確認を残した最終候補では、有効メタデータキャッシュ5000件の待受中央値が30.331秒から21.374秒へ短縮した（各3回、約29.5%減）。最初の正しいBrowseは30.493秒から21.741秒。JSON解析は数十～百msであり、主因は直列の小さなファイルアクセスだった。物理IDの事後照合を追加する前の試作では11.370秒も観測したが、採用版の性能として扱わない。

同じディレクトリのメタデータ・PCR各5000件を使う再起動測定では、待受中央値31.714秒対15.460秒、最初の正しいBrowse32.130秒対15.847秒、PCR管理API利用可能35.246秒対18.260秒だった。各3回、すべてキャッシュ利用GETに成功しPCR再生成は0件。初回はそれぞれ77.490秒／20.052秒などの外れ値もあり、中央値と条件を併記する。

有効キャッシュ照会の非同期操作は、stat 25000回＋JSON read 5000回から、stat 20000回＋JSON read 5000回へ減る。物理ID照合を前後へ分けるためソースstatは15000回を保ち、キャッシュstatを10000回から5000回へ減らす。従来の「約25000回」は主にstatだけの値であり、同期の保存先分離検査やJSON読込みを含む全操作数ではない。同期パス検査は安全性のため残す。

有効キャッシュ単独の待受時RSS中央値は約98.8MiB対97.6MiBで、重大な増加は観測していない。Node CPU時間は同シリーズで13.39秒対17.69秒であり、CPU削減とは扱わない。効果の中心はI/O待ち時間の重なりで、並列化による瞬間負荷やOS条件の影響もある。並列操作の所要時間合計を起動の実経過時間と混同しない。

PCRディレクトリ照合の独立測定では、新しい管理DBの作成が中央値4.732秒から1.304秒、既存管理DBの再照合が1.794秒から1.364秒へ短縮（各3回）。SQL prepare回数は5007回から9回へ減った。5000件のlstat、ファイル形式と通常ファイルの検査は残し、キャッシュ本文の検証は実際の索引利用時に従来どおり実施する。

新規カタログ測定では実施順によって絶対値が大きく変動した。基準版・候補を交互に測った3回では、最初の正しいBrowse中央値は29.832秒対21.741秒だった。OSキャッシュや同じPC上の他処理を完全には固定できておらず、すべてのPC・ディスクで同じ短縮率を保証しない。

## 再現用ツール

`node --import tsx tools/benchmark-startup.mjs prepare SOURCE_TREE ISOLATED_OUTPUT`

`node --import tsx tools/benchmark-startup.mjs run SOURCE_TREE ISOLATED_OUTPUT LABEL warm 3`

`warm`以外に`empty`、`missing`、`corrupt`、`fresh`を指定できる。PCR保存済みケースは`prepare-pcr`で合成索引を生成後、`pcrwarm`で測定する。出力先は専用の隔離ディレクトリを使う。生の結果・パス・実録画由来の情報は公開ソースへ含めない。

## 残る課題

保存先分離の同期canonical-path検査、実際のファイルI/O、カタログ探索は残る。背景SI解析の帯域・直列化・再生優先は従来どおりで、旧キャッシュの番組証拠補完には全編読取りが必要な場合がある。大規模ライブラリ全体の番組資源準備時刻は、起動完了とは別の指標である。

初回補完／破損回復の未達を追加調査し、単独HTTP試験でもatomic renameのWindows EPERMを採取した。解析完了後のキャッシュ置換で失敗し、通常の60秒再試行待ちへ入るため、30／45秒の試験期限では未達になる。Nodeの宛先読取りハンドルを保持すると同じEPERMを再現でき、v0.4.4の単発renameにも同じ制約がある。元の自然発生時にハンドルを保持した主体までは特定していない。

WindowsのEPERM／EBUSYに限り、旧キャッシュを残したまま最大5回（待機20／40／80／160ms）のatomic置換を試みる。待機後は保存先分離・source物理ID・size/mtimeを再検証し、変更時は破棄する。永続ロックや他のI/O異常は従来どおり失敗させ、一般の再試行間隔や監査条件は変えない。一時ファイルは成功・失敗とも後始末し、通常のlookup／起動時照会は変更しない。実際の読取りロックによる回復、永続ロック、source変更、I/O異常、停止中の処理回収をテストする。

修正前の単独HTTP試験は3回中1回が補完待ちで未達、両版同時の全テストは両方成功した。修正後は単独HTTPを10回実行してすべて成功し、そのうち実際のEPERMを記録した1回も約32ms後に同じ書込みで回復した。Public全682件の並列度1、およびPrivate757件／Public682件の両版同時・各並列度4も失敗・スキップ0件。タイムアウトや期待値は変更していない。新しい5件の契約試験は一時的／恒久的な読取りハンドル、source変更、他のI/O異常、停止中の回収を扱う。

最初に報告された過去1回の詳細証拠は不足しており、今回再現した未達と完全に同因とは断定しない。テスト間の一時データ・ポートは分離され、再現例ではSQLite異常、source版不一致、重複解析を直接原因とする証拠はない。負荷が発生率を変える可能性はあるが、単純なCPU飽和による期限不足として片付けない。Windowsでの短時間の置換拒否への耐性不足を最小修正したもので、恒久的なアクセス拒否や長時間の外部ロックまで解消するものではない。

追加修正後にも同じ合成5000件を再測定した。メタデータ単独の一括3回では修正前20.150秒／修正後24.958秒、順序を交互にした3対では29.843秒／26.515秒で、差の方向が逆転した。OSキャッシュは強制排除せず、PC全体の負荷も完全固定できていないため、小さな差を修正の高速化・退行とは断定しない。保存済みメタデータ＋PCRの3回では修正前25.269秒／修正後23.743秒だった。以前の21.374秒／15.460秒という絶対値の再現とは扱わない。

通常照会のsource stat15000＋cache stat5000＋JSON読込み5000回は維持され、追加の待機・置換処理はキャッシュhitの起動経路では実行されない。交互測定の待受時RSS中央値は修正前97.67MiB／修正後97.70MiB。PCR管理DB初回構築は中央値1.151秒（以前1.304秒）、prepare9回を維持。5000件の件数、Browseの正規化hash、Metadata、保存済みPCRでのGET／再生成0を確認した。
