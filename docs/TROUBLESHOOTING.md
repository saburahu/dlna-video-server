# 症状別の確認方法

[README](../README.md) ／ [導入](SETUP.md) ／ [ログの採り方](LOGS.md)

まずサーバーPCで管理画面を開けるか確認します。既定は `http://localhost:19090`。以下の「候補」は原因の断定ではありません。端末がフリーズ・再起動した場合は、その試験を終了し、同じ操作を繰り返さないでください。

## サーバーが見つからない

管理画面も開けない場合はStart.cmdの出力とDiagnose.cmdを確認します。Setupが起動済みなら二重にStartしません。ポートを変更した場合は管理画面のURLも変わります。

管理画面は開けるのにテレビから見えない場合の候補は、異なるLAN、無線APの端末間通信制限、VPN／複数NICの選択、SSDP multicast、Windows Firewallです。「設定」のLAN側IPv4がテレビと同じLANのサーバー側アドレスか確認し、同梱runtimeのnode.exeをプライベートネットワークで許可します。ファイアウォール全体の無効化やインターネットへのポート転送は不要です。

サーバーPCのスリープ中は利用できません。名前を変えた直後は端末のサーバー一覧を開き直してください。

## サーバーは見えるが番組がない

「録画番組」→「すべて／フォルダ別」を開きます。「設定」の録画フォルダー（1行1件）と読み取り権限を確認します。管理画面「番組一覧」の「全メディアを再スキャン」、または定期更新を待ちます。新規導入の既定は30分、保存済みの間隔は保持されます。NASは起動したWindowsユーザーで読める必要があります。

MP4等は軽量probe後に再生可能なresourceを公開します。登録直後は処理を待って一覧を再取得してください。管理画面のダッシュボードで総数・内訳・探索/codec解析状態を確認してください。通常TSの表だけではMP4等の登録有無を判断できません。[スキャン状態](MEDIA-SCAN.md)も参照してください。

resourceを出せないクライアント・ソース構成もあります。拡張子が対応形式でも、DRM、破損、未対応codec、受信能力の証拠不足なら公開されない場合があります。Browse失敗／項目がない／選択後の失敗を分けて報告してください。

## 選択すると「再生できません」になる

機器の一覧を開き直し、以前発行されたURLを使い続けていないか確認します。[対応実績](COMPATIBILITY.md)を参照してください。機種名だけでは配信方式を決めず、通信fingerprintと能力の証拠で選択しています。

JITは最大2本です。別の3本目はbusyとして拒否され、端末では一般的な再生エラーに見えることがあります。ほかの端末の不要な再生を停止してから試します。通常TSとVLC Direct PlayはこのJIT枠を使いません。

ログでBrowse、GETの有無、HTTPステータス、拒否理由を区別できます。GETがない場合と、GET後にデコードできない場合を同じ原因として扱わないでください。

## 再生画面は黒画面・無音

サーバーが本文を送ったことは端末のデコード成功の証明ではありません。まず停止して戻れるか確認し、対象形式・機器・時刻を記録します。受信profile、映像／音声codec、入力の破損などが候補です。独自にprofile名を偽装したり、MPEG-2 PSへ変換したりする対処は案内していません。

## AVIで帯状・タイル状に映像が崩れる

55X9900Rでは、msmpeg4v3・SD解像度・約23.976fpsのAVIに、低fpsのAVC JITで帯状の映像破綻が出る実例があります。同じ素材はZP2で正常でした。対象個体だけ29.97fps CFRへ補正した実JITでは、映像・音声とTimeSeekの成功を確認しています。

同じ条件・症状の場合、テレビで一度サーバーの一覧を取得し、再生を止めた状態で管理画面「クライアント」→「認識済みクライアントを更新」→対象個体の「補正を有効化」を選びます。テレビで一覧を再取得してから再生します。個体の識別が不確実な場合は有効化できないことがあります。

この設定は該当入力だけに適用されます。すべてのAVI／23.976fps動画への補正ではありません。別のcodec・症状まで同じ原因と断定せず、不要なら「補正を無効化」に戻してください。

## 再生開始に時間がかかる

通常TSの初回GETでは、PCR索引がなければ全編の索引生成完了を待つ場合があります。HDD上の大きな録画では時間がかかります。Browse自体は索引生成を待ちません。

MP4等のJITは、入力検査・FFmpeg起動・初期バッファにも時間が必要です。開始待ちと、再生中の配信不足は別の問題です。CPU負荷、ディスクやNASの速度、同時JIT数、診断ログを確認してください。キャッシュの全削除は待ち時間を増やすため、初手の対処にはしません。

## PCR索引とSeek

### タイムバーがない／TSをSeekできない

索引未生成時は、正確なdurationや時間Seek情報を一覧に出せない場合があります。一覧取得後に索引が完成しても、端末が最初の情報を保持すると、再生中のタイムバーへ反映されないことがあります。実運用で「初回はバーなし・Seek不可、停止後の再生では有効」となる例を確認しています。全機器で必ず同じ挙動とは限りません。

管理画面「PCRキャッシュ」で対象の準備を確認し、再生を停止→端末の番組一覧を再取得→再生してください。推測の長さを広告して回避する方式にはしていません。索引があるのに失敗する場合は、番組・Seek位置・時刻を記録します。HTTP要求の成功だけでは画面の復帰を保証しません。

JITのSeekは別の処理です。元動画の破損や終端、端末の要求、変換処理を調べる必要があります。VLC Direct Playは主にHTTP byte Rangeを利用し、DLNAの時間指定Seekとは異なります。

### PCR索引が生成されない

「PCRキャッシュ」で有効／一時停止、処理待ち、保留理由、空き容量、現在の対象を確認します。再生・JIT中は配信が優先されます。書き込み中の録画、更新直後、NAS切断、空き容量不足等では保留します。必要なら「再開」し、アイドル時間を確保してください。

既定の読み込み制限は32MiB/s、更新後の安定待ちは120秒、再生後の待機は15秒です。索引キャッシュ容量は既定で無制限ですが、空き容量2GiBの保護があります。実際の設定値は管理画面を確認してください。無制限時に容量理由で有効索引をLRU削除しません。録画が確実に消えた索引だけ安全条件で清掃します。

スキャン失敗やNAS切断を理由に元録画やキャッシュを手動で一括削除しないでください。待機が長い場合は停止理由と[ログ](LOGS.md)を採ります。

## JIT変換が失敗する

FFmpeg／ffprobeの両方を同じbuildから配置し、Diagnose.cmdを実行します。必要encoderがないbuild、未対応codec、入力破損、CPU／ディスク不足、busy、端末識別の不一致などをログで区別します。FFmpegの終了コードだけで正常性を判断しません。元ファイルを上書きする修復コマンドは実行しないでください。

## FFmpegが認識されない

[FFmpeg導入手順](FFMPEG.md)のチェック表を参照してください。ZIPを全部展開し、ffmpeg.exeとffprobe.exeのある**binフォルダ**をSetupへ指定します。引用符や環境変数表記を入力欄へ入れず、停止後に再設定します。

## 別PCから管理画面を開けない

**v0.2.0の管理画面・管理APIはlocalhost限定です。仕様による制限です。** サーバーPC自身で `http://localhost:19090` を開いてください。ポートを変更した場合はその番号を使います。DLNAの閲覧・動画配信はLANから利用できます。管理のためにインターネットへポートを公開しないでください。

## Setupが失敗する／停止を求められる

`Stop this data directory before setup/import/backup` は同じデータでDMSが稼働中のため、安全に拒否した状態です。全端末の再生を終了して、そのアプリのStop.cmdで停止します。稼働中ロックを手動削除したり、ほかのNodeプロセスをまとめて終了したりしないでください。

Setupのエラーが出た場合は、最後の「何かキーを押してください」を成功と解釈しないでください。v0.2.0のSetup.cmdは失敗時でも終了コード0となる場合がありました。**v0.2.1で修正済み**で、成功時0、失敗時非0を返します。エラーの詳細は画面でも確認してください。Start／Stop／Backup等の他CMDラッパーの終了コードは今回の修正対象外です。


v0.2.3の端末探索復旧については[詳しい説明](CLIENT-DISCOVERY.md)を参照してください。既存の設定・UDN・catalog・PCR索引は保持します。
